## Part 1 — Cloud Concepts (25–30% of exam)

### Module 1.1 — What is Cloud Computing?

Cloud computing means using someone else's computers (Microsoft's data centers) over the internet instead of buying and running your own hardware.

**Shared responsibility model** — who is responsible for what:

| | On-premises (your own server) | Cloud |
|---|---|---|
| Physical hardware | You | Microsoft |
| Network | You | Microsoft |
| Operating system | You | Shared or Microsoft |
| Your data | You | Always you |
| Your application | You | You |

The more managed the service, the more Microsoft handles. The less you manage, the less control you have.

**Two cost models:**

- **CapEx (Capital Expenditure)** — you buy hardware upfront. Big cost now, lower cost later. Traditional on-premises.
- **OpEx (Operational Expenditure)** — you pay monthly as you use it. No big upfront cost. This is the cloud model.

Cloud is OpEx. You pay only for what you use.

---

### Module 1.2 — Benefits of Cloud Services

**High availability** — the service stays running even if something breaks. Microsoft guarantees this with an SLA (Service Level Agreement) — a promise that the service will be up a certain % of the time (e.g. 99.9%).

**Scalability** — the ability to handle more or less load:
- **Scale up (vertical)** — give the same machine more CPU/RAM
- **Scale out (horizontal)** — add more machines

**Elasticity** — automatically scale up when busy, scale down when quiet. You don't overpay for capacity you don't need.

**Reliability** — your app keeps working even if one data center fails. Azure spreads resources across multiple locations.

**Security** — Microsoft handles the physical security of data centers. You control who can access your resources (RBAC, Entra ID).

**Governance** — rules and policies you enforce across your Azure resources (e.g. "no storage accounts without encryption").

**Manageability** — you can manage everything through the portal, CLI, or code — and Azure monitors your resources automatically.

---

### Module 1.3 — Cloud Service Types

Three types — think of them as how much you manage vs how much Microsoft manages.

**IaaS — Infrastructure as a Service**
- You get: virtual machines, networking, storage
- You manage: OS, middleware, your app, your data
- Microsoft manages: physical hardware
- Example: Azure Virtual Machines
- Analogy: renting an empty office space — you bring your own furniture

**PaaS — Platform as a Service**
- You get: a platform to run your app
- You manage: your app and your data only
- Microsoft manages: OS, runtime, patching, scaling
- Example: Azure App Service, Azure SQL Database, Azure Functions
- Analogy: renting a furnished office — you just bring your laptop

**SaaS — Software as a Service**
- You get: a fully working application
- You manage: nothing (maybe your settings and data)
- Microsoft manages: everything
- Example: Microsoft 365, Outlook, Teams
- Analogy: using a hotel room — everything is provided

| | IaaS | PaaS | SaaS |
|---|---|---|---|
| You manage | Most | Some | Almost nothing |
| Flexibility | Highest | Medium | Lowest |
| Effort | Highest | Medium | Lowest |

## Part 2 — Azure Architecture and Services (35–40% of exam)

### Module 2.1 — Core Azure Architecture

**Azure is organized in a hierarchy:**

```
Tenant (your organization in Entra ID)
└── Management Group (optional grouping of subscriptions)
      └── Subscription (billing boundary)
            └── Resource Group (logical folder for resources)
                  └── Resource (actual service: VM, Storage, etc.)
```

- **Tenant** — your company's identity home. One per organization.
- **Subscription** — your billing account. All costs go here.
- **Resource Group** — a folder that groups related resources. Delete the group and everything inside is deleted.
- **Resource** — the actual thing (a VM, a database, a storage account).

**Regions and Availability Zones:**

- **Region** — a physical location of Azure data centers (e.g. West Europe = Netherlands, North Europe = Ireland)
- **Availability Zone** — separate buildings within one region with independent power, cooling, and networking. Deploy across zones for high availability.
- **Region Pair** — two regions paired together for disaster recovery (e.g. West Europe ↔ North Europe). If one goes down, the other takes over.

**Rule of thumb:** Put resources in the same region unless you have a reason not to. It keeps latency low and avoids cross-region data transfer costs.

### Module 2.2 Deep Dive — Compute

#### Virtual Machines (VMs) — in depth

A VM is a computer running inside Microsoft's data center. You choose the size (CPU + RAM), the operating system (Windows or Linux), and the disk. You connect to it remotely and use it like a real computer.

**VM sizes — how to read them:**

Azure VM names follow a pattern: `Standard_B2s`, `Standard_D4s_v5`, etc.

| Letter | What it means |
|---|---|
| **B** | Burstable — cheap, good for dev/test, can spike CPU briefly |
| **D** | General purpose — balanced CPU and RAM, most common |
| **E** | Memory optimized — more RAM, for databases |
| **F** | Compute optimized — more CPU, for processing workloads |
| **The number** | How many vCPUs (e.g. D**4** = 4 vCPUs) |
| **s** | Premium SSD disk supported |

For AZ-900 learning: `Standard_B1s` is the cheapest (~$7/month) and enough to practice.

**VM disks:**

Every VM has at least two disks:
- **OS disk** — where Windows or Linux is installed
- **Temporary disk** — fast, but data is lost when the VM restarts (do not store important data here)
- **Data disk** — optional extra disk you attach for your data (persists across restarts)

Disk types by speed and cost:
| Type | Speed | Cost | Use for |
|---|---|---|---|
| **Standard HDD** | Slowest | Cheapest | Backups, archiving |
| **Standard SSD** | Medium | Medium | Dev/test VMs |
| **Premium SSD** | Fast | Higher | Production workloads |
| **Ultra Disk** | Fastest | Most expensive | Databases needing very low latency |

**VM availability options:**

The problem: if one VM crashes, your app goes down. The solution:

- **Availability Set** — spreads your VMs across different physical racks in the same data center. Protects against hardware failure in one rack.
- **Availability Zone** — spreads your VMs across separate buildings in one region. Protects against an entire building going down.
- **Virtual Machine Scale Sets (VMSS)** — automatically creates or deletes VMs based on demand. If traffic goes up, Azure adds VMs automatically. If traffic drops, it removes them. This is how auto-scaling works.

```
One VM alone → single point of failure (avoid in production)

Availability Set → protected from rack failure (same building)
Availability Zone → protected from building failure (same region)
VMSS → automatically scales the number of VMs up and down
```

#### App Service — in depth

App Service is a managed platform for running web apps. You give Azure your code or a Docker container, and Azure runs it — no VM to manage, no OS to patch.

**App Service Plans** — you don't pay for the app, you pay for the plan (the underlying compute):

| Plan | Cost | What you get |
|---|---|---|
| **Free (F1)** | Free | 60 min/day CPU, no custom domain, shared hardware |
| **Shared (D1)** | ~$10/month | Custom domain, shared hardware |
| **Basic (B1/B2/B3)** | ~$13–52/month | Dedicated hardware, manual scaling |
| **Standard (S1/S2/S3)** | ~$73+/month | Auto-scaling, staging slots, backups |
| **Premium** | Higher | Faster hardware, VNet integration |

**Key feature — Deployment Slots:**
You can have a "staging" version of your app and a "production" version. You test in staging, then **swap** them — zero downtime deployment. If something breaks, swap back.

```
staging slot ←→ production slot   (swap with one click)
```

**What App Service supports:**
- Python, .NET, Node.js, Java, PHP, Ruby
- Docker containers
- GitHub Actions / Azure DevOps deployments (push code → app updates automatically)

---

#### Azure Functions — in depth

A Function is a single piece of code that runs when something happens (a trigger). You don't manage any server — Azure runs it and you pay only for the time it actually executes.

**Triggers — what can start a Function:**

| Trigger | When it fires |
|---|---|
| **HTTP trigger** | Someone calls a URL (like an API endpoint) |
| **Timer trigger** | On a schedule (e.g. every day at 6am) |
| **Blob trigger** | When a file is uploaded to Azure Storage |
| **Queue trigger** | When a message arrives in a Queue |
| **Event Hub trigger** | When a stream of events arrives (e.g. IoT data) |

**Hosting plans — how Azure Functions runs:**

| Plan | How it works | Cold start? |
|---|---|---|
| **Consumption** | Pay per execution, scales to zero when idle | Yes — first call after idle is slow |
| **Premium** | Always-warm instances, no cold start | No |
| **Dedicated (App Service)** | Runs on your App Service Plan | No |

For AZ-900: Consumption plan is free for 1M executions/month and is the default.

**Cold start** = when a Function hasn't been called in a while, Azure shuts it down to save resources. The next call takes a few seconds longer to start up. This is a trade-off of the serverless model.

---

#### Containers — ACI vs AKS

**What is a container?**
A container is a package of your app + everything it needs to run (code, libraries, settings). It runs the same way everywhere — on your laptop, in Azure, anywhere. Docker is the tool used to build containers.

**Azure Container Instances (ACI):**
- Runs a single container — no cluster, no configuration
- Starts in seconds
- You pay per second the container runs
- Good for: one-off jobs, batch processing, testing

**Azure Kubernetes Service (AKS):**
- Manages many containers across many machines
- Handles: restarting crashed containers, scaling, load balancing, rolling updates
- Good for: production apps made of multiple services (microservices)
- More complex to set up than ACI

**Simple decision:**

```
One container, short task → ACI
Many containers, production app → AKS
Just a web app or API → App Service (simpler than both)
```

### Module 2.2 Deep Dive — Networking

#### Virtual Network (VNet) — in depth

A VNet is your own private network inside Azure. Resources inside the same VNet can talk to each other using private IP addresses — like computers on the same office Wi-Fi. Nothing from outside can get in unless you explicitly allow it.

**Subnets — dividing the VNet:**

You split a VNet into subnets to separate and secure different parts of your system:

```
VNet: 10.0.0.0/16
├── Subnet: web-tier      10.0.1.0/24   ← public-facing web servers
├── Subnet: app-tier      10.0.2.0/24   ← backend application servers
└── Subnet: data-tier     10.0.3.0/24   ← databases (most protected)
```

The web tier can talk to the app tier. The app tier can talk to the data tier. But the web tier cannot talk directly to the data tier — the subnet separation enforces this.

**VNet Peering:**
Connect two VNets so resources in both can talk to each other using private IPs. Used to connect a dev VNet to a shared services VNet, for example.

---

#### Network Security Groups (NSGs) — in depth

An NSG is a list of rules that control traffic in and out of a subnet or a single VM.

Each rule has:
- **Priority** — lower number = checked first (100 beats 200)
- **Source** — where traffic comes from (IP address, a whole subnet, "Any")
- **Destination** — where it's going
- **Port** — which port (80 = HTTP, 443 = HTTPS, 22 = SSH, 3389 = RDP)
- **Protocol** — TCP or UDP
- **Action** — Allow or Deny

**Example NSG rules for a web server:**

| Priority | Direction | Source | Port | Action | Reason |
|---|---|---|---|---|---|
| 100 | Inbound | Any | 443 | Allow | Let HTTPS traffic in |
| 110 | Inbound | Any | 80 | Allow | Let HTTP traffic in |
| 200 | Inbound | Any | 22 | Deny | Block SSH from internet |
| 65000 | Inbound | Any | Any | Deny | Block everything else |

Default rule (Azure adds automatically): Allow traffic within the VNet, Deny everything from internet unless explicitly allowed.

---

#### Load Balancer vs Application Gateway

Both distribute traffic across multiple VMs, but they work at different levels:

**Azure Load Balancer:**
- Works at the network level (Layer 4 — TCP/UDP)
- Distributes traffic based on IP and port
- Very fast, no understanding of HTTP
- Good for: non-HTTP traffic, internal load balancing between VMs

**Azure Application Gateway:**
- Works at the application level (Layer 7 — HTTP/HTTPS)
- Can route based on URL path (`/api` goes to one set of VMs, `/images` to another)
- Has a built-in **Web Application Firewall (WAF)** — blocks common attacks (SQL injection, XSS)
- Good for: web apps and APIs exposed to the internet

```
User → Application Gateway (understands HTTP, has WAF) → VMs
User → Load Balancer (fast, simple, no HTTP awareness) → VMs
```

---

#### Connecting to Azure from your office

Two ways to connect your on-premises network (your office) to Azure:

**VPN Gateway:**
- Uses the internet but encrypts all traffic (like a secure tunnel)
- Cheaper
- Slower than ExpressRoute
- Good enough for most companies

**ExpressRoute:**
- A private physical cable from your office to Microsoft's network — never touches the internet
- More expensive (you pay the telecom provider for the dedicated line)
- Faster and more reliable — guaranteed bandwidth
- Required for companies with strict compliance (banks, hospitals) or very high data volumes

```
Office → internet → encrypted VPN tunnel → Azure     (VPN Gateway)
Office → private cable → Microsoft network → Azure   (ExpressRoute)
```

---

#### Azure CDN and Traffic Manager

**Azure CDN (Content Delivery Network):**
Copies your static files (images, videos, JavaScript) to servers around the world. When a user in Japan visits your site, they get the files from a server in Japan instead of your server in West Europe — much faster.

**Azure Traffic Manager:**
Directs users to the closest or healthiest Azure region. If your app runs in both West Europe and East US, Traffic Manager sends European users to West Europe and American users to East US. It also detects if one region is down and redirects traffic automatically.

### Module 2.3 Deep Dive — Storage

#### Blob Storage — in depth

**Blob** stands for Binary Large Object — it's just any file. Blob Storage is Azure's general-purpose file storage. Think of it like a hard drive in the cloud, but accessible from anywhere via a URL.

**Structure of Blob Storage:**

```
Storage Account  (the top-level container — has a unique name)
└── Container  (like a folder — you can have many)
    ├── blob1.csv
    ├── blob2.parquet
    └── subfolder/blob3.json
```

- **Storage Account** — the root. Its name becomes part of every URL: `https://mystorageaccount.blob.core.windows.net`
- **Container** — a bucket inside the storage account. Set access to private or public.
- **Blob** — the actual file inside a container.

**Three types of blobs:**

| Type | What it is | Use for |
|---|---|---|
| **Block Blob** | Standard file storage — uploaded in blocks | Documents, images, videos, Parquet files — the default |
| **Append Blob** | Can only add data to the end — cannot edit the middle | Log files (you only ever add new lines) |
| **Page Blob** — | Random read/write access | VM disks (Azure uses this internally for OS and data disks) |

For data engineering work, you always use **Block Blobs**.

**Access tiers — controlling cost vs speed:**

You don't always need instant access to all your files. Older data can be stored cheaper:

| Tier | Access speed | Cost | Use for |
|---|---|---|---|
| **Hot** | Instant | Higher storage cost, lower access cost | Files you read frequently |
| **Cool** | Instant | Lower storage cost, higher access cost | Files you read less than once a month |
| **Cold** | Instant | Even lower storage | Files you read less than once every 90 days |
| **Archive** | Hours (must be rehydrated first) | Cheapest | Compliance backups you almost never read |

**Lifecycle Management** — you can set a rule to automatically move files between tiers:
> "After 30 days, move to Cool. After 90 days, move to Archive. After 365 days, delete."

This runs automatically — you don't do it manually.

**Blob Storage access control:**

Two ways to control who can access blobs:

1. **Storage Account Key** — a master password. Whoever has it has full access to everything. Avoid using this in code — if it leaks, everything is exposed.
2. **Shared Access Signature (SAS)** — a temporary URL with limited permissions. You can create a URL that lets someone download one specific file for the next 2 hours only. After 2 hours, the link stops working.

```
SAS URL example:
https://mystorageaccount.blob.core.windows.net/data/file.csv
  ?sv=2023-01-01&st=2026-08-30T10:00Z&se=2026-08-30T12:00Z&sp=r&sig=abc123

sv = storage version
st = start time
se = expiry time  (this link dies at 12:00)
sp = permissions  (r = read only)
sig = signature   (proves the URL wasn't tampered with)
```

For production code: always use **Managed Identity + RBAC** instead of keys or SAS. Keys are for quick testing only.

#### Azure Data Lake Storage Gen2 (ADLS) — in depth

ADLS Gen2 is Blob Storage with one major upgrade: a **hierarchical namespace**. This means real folders with proper permissions — you can set access on a specific folder, not just the whole container.

**Why this matters for data engineering:**

In regular Blob Storage, "folders" are fake — they're just part of the filename. `raw/2026/08/data.csv` looks like a folder structure but it's actually one filename. You can't set permissions on `raw/` specifically.

In ADLS Gen2, `raw/` is a real folder. You can say: "the ingestion pipeline can write to `raw/` but can only read from `silver/`". This is the **Medallion Architecture** enforced at the storage level.

```
ADLS Gen2 Container
├── raw/           ← ingestion pipeline has Write here
│   └── 2026/08/sales.csv
├── silver/        ← cleaning pipeline has Read on raw/, Write here
│   └── 2026/08/sales_clean.parquet
└── gold/          ← aggregation pipeline has Read on silver/, Write here
    └── 2026/08/sales_summary.parquet
```

ADLS Gen2 also supports **Access Control Lists (ACLs)** — fine-grained permissions on individual files and folders, on top of RBAC.

#### Azure Files — in depth

Azure Files is a fully managed **network file share** in the cloud. It uses the SMB protocol (the same as Windows shared folders). You can "mount" it on a Windows or Linux machine and it appears as a drive letter (like `Z:\`) or a folder.

**When to use Azure Files vs Blob Storage:**

| | Blob Storage | Azure Files |
|---|---|---|
| Access method | HTTP/SDK | Mount as a drive (SMB) or HTTP |
| Best for | Apps reading files via code | Apps that expect a regular file system |
| Legacy app support | No | Yes — old apps that use file paths work without changes |
| Shared across VMs | Via SDK | Yes — multiple VMs mount the same share |

**Use case example:** You have an old application that reads config files from `C:\configs\`. You can't easily rewrite it. You move those configs to Azure Files, mount it as `C:\configs\` on your VM — the app works without any code changes.

#### Azure Queues and Storage redundancy — in depth

**Azure Queue Storage:**

A queue is like a to-do list for your system. One service puts a message in the queue ("process this file"). Another service picks up messages and processes them one by one. The two services never talk to each other directly — the queue sits between them.

```
Data ingestion service  →  puts message in Queue  →  Processing service reads it
```

Why this is useful:
- If the processing service crashes, messages stay in the queue — nothing is lost
- You can scale the processing service independently
- The ingestion service doesn't slow down waiting for processing to finish

**Queue vs Service Bus:**

| | Azure Queue Storage | Azure Service Bus |
|---|---|---|
| Complexity | Simple | More features |
| Message ordering | Not guaranteed | Guaranteed (FIFO) |
| Max message size | 64 KB | 256 KB – 100 MB |
| Use for | Simple task queues | Enterprise messaging, ordered workflows |

For AZ-900: just know Queue Storage = simple messaging between services.

---

**Storage redundancy — in depth:**

When you create a storage account, you choose how many copies Azure keeps and where:

```
LRS — 3 copies, 1 data center, 1 region
   [DC1: copy1, copy2, copy3]

ZRS — 3 copies, 3 availability zones, 1 region
   [Zone1: copy1]  [Zone2: copy2]  [Zone3: copy3]

GRS — 6 copies, 2 regions (primary + paired region)
   Primary region: [DC1: copy1, copy2, copy3]
   Paired region:  [DC1: copy4, copy5, copy6]

GZRS — 6 copies, 3 zones in primary + 1 data center in paired region
   Primary: [Zone1][Zone2][Zone3]
   Paired region: [DC1: copy4, copy5, copy6]
```

**Which to choose:**

| Scenario | Recommended |
|---|---|
| Dev/test, low cost | LRS |
| Production, protect against zone failure | ZRS |
| Production, protect against regional disaster | GRS or GZRS |
| Compliance requiring cross-region backup | GRS or GZRS |

**Read-access GRS (RA-GRS):** With normal GRS, the paired region copy is only accessible if Microsoft declares a failover. With RA-GRS, you can read from the paired region copy at any time — useful for globally distributed read-heavy apps.

---

**Identity — Microsoft Entra ID:**

Entra ID (formerly Azure AD) is the identity system. It controls who can sign in and what they can access.

- **User** — a person with a username and password
- **Group** — a collection of users — assign roles to the group, everyone inside inherits them
- **Service Principal** — a non-human identity for an application or script
- **Managed Identity** — a Service Principal that Azure manages automatically — no passwords needed in your code

**Authentication vs Authorization:**
- **Authentication** — proving who you are (sign in with username + password)
- **Authorization** — what you are allowed to do after signing in (RBAC role)

**RBAC — Role-Based Access Control:**
You assign a role to an identity at a scope (resource, resource group, subscription).

| Role | What it can do |
|---|---|
| Owner | Everything including changing access |
| Contributor | Create and manage resources, cannot change access |
| Reader | View only, cannot change anything |

Roles assigned at a higher level (subscription) flow down to everything below (resource groups and resources).

**Security tools:**

| Tool | What it does |
|---|---|
| **Microsoft Defender for Cloud** | Monitors your Azure resources for security issues and gives a security score |
| **Azure Key Vault** | Stores secrets (API keys, passwords, certificates) securely — your code retrieves them at runtime |
| **Azure DDoS Protection** | Protects your app from DDoS attacks (flooding your service with traffic) |

## Part 3 — Azure Management and Governance (30–35% of exam)

### Module 3.1 — Cost Management and Pricing

**How Azure pricing works:**

- You pay for what you use — compute (per hour/second), storage (per GB), network (per GB transferred out)
- Some services have a free tier — Azure Functions (1M requests/month free), Blob Storage (first 5 GB free)
- Prices vary by region — West Europe is often slightly more expensive than East US

**Ways to reduce costs:**

| Method | How it saves money |
|---|---|
| **Reserved Instances** | Pay 1 or 3 years upfront for a VM — save up to 72% vs pay-as-you-go |
| **Spot Instances** | Use spare Azure capacity at huge discounts — Azure can take it back with 30 seconds notice |
| **Azure Hybrid Benefit** | Use your existing Windows/SQL Server licenses on Azure VMs — saves up to 40% |
| **Dev/Test pricing** | Cheaper rates for non-production workloads |

**Free tools to estimate and monitor costs:**

- **Azure Pricing Calculator** — estimate costs before you create anything (`azure.microsoft.com/pricing/calculator`)
- **Total Cost of Ownership (TCO) Calculator** — compare your current on-premises cost vs Azure
- **Azure Cost Management** — monitor and analyze what you're actually spending inside the portal
- **Budget Alerts** — get an email when your spending hits a threshold you set

---

### Module 3.2 — Governance and Compliance

Governance = making sure everyone follows the rules in your Azure environment.

**Azure Policy:**
Rules that enforce standards across your Azure resources. Automatically checks if resources comply and can block non-compliant ones.

Examples of policies:
- "All storage accounts must have encryption enabled"
- "Resources can only be created in West Europe"
- "Virtual machines must use approved VM sizes only"

Policies are assigned at a scope (Management Group, Subscription, or Resource Group) and apply to everything below.

**Azure Blueprints:**
A package of policies, role assignments, and resource templates deployed together. Used to set up a new environment consistently (e.g. spin up a new subscription that already has all your company's policies and standard resources).

**Resource Locks:**
Prevent accidental deletion or modification of resources.
- **CanNotDelete** — people can read and modify but cannot delete
- **ReadOnly** — people can only read, cannot modify or delete

**Microsoft Purview:**
A governance tool for tracking where your data lives, who can access it, and what kind of data it is (personal, sensitive, etc.). Used for compliance (GDPR, ISO, etc.).

**Compliance in Azure:**
Microsoft maintains certifications for their data centers — ISO 27001, SOC 2, GDPR compliance, etc. You can view all compliance certifications in the **Microsoft Trust Center**.

## Quick Revision — what the exam tests

| Topic | Key thing to remember |
|---|---|
| IaaS / PaaS / SaaS | Who manages what |
| CapEx vs OpEx | On-prem = CapEx, Cloud = OpEx |
| Availability Zones | Separate buildings in one region — for high availability |
| Region Pairs | Two regions for disaster recovery |
| Resource Group | Logical folder — delete it and everything inside goes |
| RBAC | WHO + WHAT role + WHERE scope |
| Managed Identity | App identity with no passwords — always preferred |
| Azure Policy | Enforces rules on resources automatically |
| Resource Lock | Prevents accidental delete or modify |
| LRS / GRS | How many copies of your data Azure keeps |
| SLA | Microsoft's uptime promise — usually 99.9% or higher |
| Cost Management | Pricing Calculator = estimate. Cost Management = actual spend. |
| Reserved Instances | 1 or 3 year commitment = big discount on VMs |
